## Оптимізація споживання пам'яті

За основу взято попередню версію: рефакторинг `SorcerStone/src/Main.java`, підрахунок
30 найчастіших слів у книзі `harry.txt`. Порівнюються три версії:

| Версія | Що це | Де лежить |
|---|---|---|
| v1 | початковий код із GitHub | `original/Main.java.txt`, для бенчмарку `bench/v1/OriginalMain.java` |
| v2 | попередній рефакторинг (`HashMap` + регулярний вираз) | `bench/v2/` |
| v3 | ця робота, оптимізація пам'яті | `src/` |

У `bench/v1` алгоритм скопійовано без змін, параметрами стали лише шлях до файлу та
потік виводу. `bench/v2` — дослівна копія попередньої версії, додано лише `package v2;`
і `public` у `Main.run`, щоб бенчмарк міг її викликати.

## Пропозиції

| № | Що витрачало пам'ять у v2 | Як зроблено у v3 |
|---|---|---|
| 1 | `readLine()` створює новий `String` на кожен рядок файлу. | Файл читається блоками в один буфер `byte[8192]`, який перевикористовується. |
| 2 | `Reader` декодує Windows-1252 у `char`, хоча значення мають лише ASCII-літери. | Обробляються сирі байти: будь-який байт поза `A-Z`/`a-z` є роздільником. Результат такий самий для будь-якого ASCII-сумісного кодування, тому `Charset` у `Main` більше не потрібен. |
| 3 | `Pattern`/`Matcher` створює об'єкти на кожен рядок. | Регулярний вираз замінено перевіркою одного байта: `b \| 0x20` у діапазоні `'a'..'z'`. |
| 4 | `matcher.group()` створює `String` на кожне з 80 622 слів, `toLowerCase` — ще один для слів із великої літери. | Слово відразу в нижньому регістрі збирається в буфер, що перевикористовується. Під час підрахунку рядки не створюються взагалі. |
| 5 | У `HashMap<String, …>` неможливо знайти слово, не створивши ключ-`String`. | Власна хеш-таблиця з відкритою адресацією (`WordCounts`) шукає слово прямо за байтами з буфера. Хеш (`31 * h + c`) рахується під час читання. |
| 6 | Кожне з 5 764 унікальних слів займає кілька об'єктів: `HashMap.Node`, `String` і його `byte[]`. | Усі слова лежать підряд в одному `byte[]`, межі слів зберігаються в `int[] offsets`. Окремих об'єктів на слово немає. |
| 7 | `merge(word, 1L, Long::sum)` створює новий `Long` на кожне збільшення лічильника понад 127. | Лічильники зберігаються в `int[] counts` і збільшуються на місці, без упаковки. |
| 8 | Частоти зберігаються в `long`, хоча слів у книзі близько 80 тисяч. | Частоти зберігаються в `int`, переповнення перевіряє `Math.incrementExact`. |
| 9 | `HashMap` стартує з 16 комірок і для цієї книги 9 разів перебудовує таблицю, щоразу викидаючи стару. | Таблиця одразу розрахована на 8 192 слова, тож для цієї книги розширення не відбувається. Для більших текстів вона подвоюється. |
| 10 | `stream().map(...).sorted()` створює `WordFrequency` для всіх 5 764 слів і сортує їх заради 30 рядків. | Топ-k відбирається в масив `int[limit]` (бінарний пошук + `System.arraycopy`). `String` і `WordFrequency` створюються лише для 30 слів, що потрапили в результат. |

Вивід v3 збігається з v2 до символу; бенчмарк перевіряє це перед вимірюваннями. Вивід v1
відрізняється через його помилки, описані в попередній роботі: наприклад, слово `he` губиться,
бо `contains` знаходить його всередині `ahead`.

## Вимірювання

Середовище: AMD Ryzen 7 5700X (8 ядер / 16 потоків), 32 ГБ RAM, Windows 10, OpenJDK 25.0.2.
Сирий результат збережено в `SorcerStone/bench/results.txt`.

| Версія | Холодний запуск, мс | Прогрітий JVM, мс (медіана) | Прогрітий JVM, мс (мін.) | Виділено пам'яті за запуск | Структура частот у heap | Мінімальний `-Xmx` |
|---|---:|---:|---:|---:|---:|---:|
| v1 | 1519.0 | 651.18 | 642.67 | 188.49 МБ | — | 6.0 МБ |
| v2 | 60.9 | 8.69 | 8.23 | 7.23 МБ | 566 КБ | 2.0 МБ |
| v3 | **14.8** | **2.03** | **1.83** | **0.21 МБ** | **203 КБ** | 2.0 МБ |

Що означають колонки:

- **Холодний запуск**: один прогін у новому JVM, медіана з 5 JVM. Це той самий час, який
  програма друкує після `------`.
- **Прогрітий JVM**: після 50 прогонів на прогрів вимірюється 200 прогонів (для v1 — 3 і 10,
  бо один прогін триває близько секунди). Перед кожним прогоном викликається `System.gc()`.
- **Виділено пам'яті**: сума всіх об'єктів, створених за один прогін
  (`ThreadMXBean.getCurrentThreadAllocatedBytes`). Саме цю пам'ять потім прибирає GC.
- **Структура частот у heap**: скільки пам'яті займає готовий результат підрахунку (`HashMap` у v2,
  `WordCounts` у v3) після повного GC. Для v1 такої окремої структури немає.
- **Мінімальний `-Xmx`**: найменший heap (з точністю до 1 КБ), з яким прогін завершується успішно.
  2 МБ — це нижня межа самого JVM (`-Xmx1500k` дає «Too small maximum heap»), тобто v2 і v3
  обидві вміщуються в мінімум, а v1 потребує втричі більше.

## Порівняння

| | v3 порівняно з v2 | v3 порівняно з v1 |
|---|---:|---:|
| Виділено пам'яті за запуск | у 34 рази менше (7.23 → 0.21 МБ) | приблизно у 900 разів менше (188.49 → 0.21 МБ) |
| Структура частот у heap | у 2.8 раза менше (566 → 203 КБ) | — |
| Час, холодний запуск | у 4 рази швидше (60.9 → 14.8 мс) | у 100 разів швидше (1519 → 14.8 мс) |
| Час, прогрітий JVM | у 4.3 раза швидше (8.69 → 2.03 мс) | у 320 разів швидше (651 → 2.03 мс) |

Майже всі 0.21 МБ, які виділяє v3, припадають на заздалегідь створені масиви таблиці.
Їхній розмір не залежить від кількості слів у тексті, тому на кожне прочитане слово v3 не
створює жодного об'єкта. Меншу кількість об'єктів видно і в часі: для v3 майже не потрібна
робота GC.

Обмеження v3, на які свідомо пішли заради пам'яті:

- Вхідний файл має бути в ASCII-сумісному кодуванні (Windows-1252, UTF-8, ISO-8859-x).
  UTF-16 не підтримується. v2 теж читала тільки Windows-1252.
- Таблиця резервує близько 200 КБ навіть для короткого тексту. Для одного великого файлу
  це вигідно, для тисяч маленьких — ні.
- Частота одного слова обмежена `int`. Якщо її перевищити, програма кине `ArithmeticException`,
  а не тихо переповниться.

## Структура

```text
SorcerStone/
  src/Main.java                   аргументи, читання файлу та звіт
  src/WordFrequencyAnalyzer.java  розбір байтів на слова і відбір топ-k
  src/WordCounts.java             хеш-таблиця слово -> частота на масивах
  src/txt/harry.txt               незмінений текст із GitHub
  test/WordFrequencyAnalyzerTest.java
  original/Main.java.txt          v1, початковий код
  bench/v1/OriginalMain.java      v1 у вигляді, придатному для бенчмарку
  bench/v2/                       v2, попередній рефакторинг
  bench/Benchmark.java            вимірювання часу та пам'яті
  bench/results.txt               результат запуску бенчмарку
```

## Запуск

Команди виконуються з каталогу `SorcerStone/`.

Тести (34 перевірки, зокрема збіг частот усіх слів книги з незалежним способом підрахунку):

```bash
javac -Xlint:all -d out/test src/*.java test/WordFrequencyAnalyzerTest.java
java -cp out/test WordFrequencyAnalyzerTest
```

Програма:

```bash
java -cp out/test Main src/txt/harry.txt 30
```

Бенчмарк (близько хвилини, найдовше працює v1):

```bash
javac -d out/bench src/*.java bench/Benchmark.java bench/v1/*.java bench/v2/*.java
java -cp out/bench Benchmark
```

Абсолютні значення часу залежать від комп'ютера й запуску, але співвідношення між
версіями на повторних запусках зберігалися. Spring Boot застосунок у корені репозиторію
не змінювався.
